# 구조와 후속 구현

## 의존 방향

```text
Next.js UI ── Next.js 서버 프록시 ─┐
MCP 도구 ────────────────────────┼─ Spring REST API ─ 서비스 ─ 저장소
GPTs / HTTP 에이전트 ────────────┘                     ├ DRY_RUN 어댑터
                                                      ├ Meta 게시 어댑터
                                                      └ 역법·운세 계산
```

백엔드가 계정 연결, 입력 검증, 초안 상태 전이, 역법 계산, 콘텐츠 생성과 게시 결과의 기준입니다. UI와 MCP는 같은 REST API를 사용합니다. OpenAPI는 `backend/src/main/resources/static/openapi.yaml` 한 곳에 관리합니다.

## 작업 공간과 연결

- 하나의 작업 공간, 플랫폼별 하나의 연결 계정을 사용합니다. 일반 공개 서비스의 사용자별 테넌트 분리는 아직 구현하지 않습니다.
- Next.js 서버가 백엔드 API 키를 주입합니다. 공개 HTTPS 프론트엔드는 `PUBLIC_APP_URL`과 동일한 `FRONTEND_ORIGIN`을 명시하고 16자 이상의 사이트 비밀번호를 설정해야 합니다. 로그인 세션은 서명되고 8시간 후 만료됩니다.
- 소셜 OAuth는 사이트 접근 인증과 별개입니다. 시작한 브라우저의 쿠키와 일회성 `state`를 확인한 뒤 서버에서 코드를 교환합니다. 앱 시크릿과 Meta 액세스 토큰은 AI 도구나 브라우저 응답에 포함하지 않습니다.
- Instagram Login은 프로페셔널 계정의 `instagram_business_basic`, `instagram_business_content_publish` 권한을 사용합니다. Threads는 `threads_basic`, `threads_content_publish`, `threads_manage_replies`를 사용합니다. 4편 게시 전에는 공식 토큰 디버그 API로 답글 권한을 확인합니다. 실제 설정은 [Meta 연결 안내](meta-setup.md)를 참조합니다.
- 계정 토큰은 서버의 32바이트 암호화 키로 암호화하여 저장합니다. 토큰 자동 갱신은 없으며 만료되면 다시 연결합니다.

## 초안·모의 실행·실제 게시

H2 파일 저장소와 Flyway 마이그레이션을 사용하며, PostgreSQL 프로필은 서버 운영을 위한 출발점입니다. 시간은 오프셋을 포함한 ISO 8601 형식으로 주고받고 브라우저 로컬 시각은 UI 경계에서 변환합니다.

| 작업 | 상태 전이 | 외부 게시 |
|---|---|---|
| 초안 생성·수정 | `DRAFT` | 없음 |
| 모의 예약 | `DRAFT → SCHEDULED` | 없음 |
| 예약 취소 | `SCHEDULED → DRAFT` | 없음 |
| 즉시 또는 예약 모의 실행 | `DRAFT/SCHEDULED → SIMULATED` | 없음 |
| 명시적 실제 게시 | `DRAFT → PUBLISHING → PUBLISHED` | Meta 게시 ID로 성공 확인 |
| 실제 게시 실패 | `PUBLISHING → PUBLISH_FAILED` | 결과 오류를 기록하고 중지 |
| 연속글 일부 게시 | `PUBLISHING → PUBLISH_PARTIAL` | 앞선 글은 공개 상태, 다음 편 준비에서 중지 |
| 실제 결과 불확실 | `PUBLISHING → PUBLISH_UNKNOWN` | 플랫폼을 직접 확인해야 함 |

15초 주기의 예약 검사와 `/dry-run`은 계정이 연결되어 있어도 모의 실행만 수행합니다. 실제 게시에는 별도 `/publish` 요청이 필요합니다. 화면의 연결 상태나 health의 `EXPLICIT_LIVE_PUBLISH`가 자동 게시를 켜는 설정은 아닙니다.

실제 게시 요청은 사용자에게 승인받은 `accountId`와 초안의 정확한 `expectedUpdatedAt`을 요구합니다. 모든 `segments`와 이미지까지 확인한 내용에 대해 승인받아야 합니다. 게시 전 계정·권한을 확인하고 `PUBLISHING`과 대상 계정을 먼저 저장한 뒤 컨테이너 생성 → 처리 상태 확인 → 게시 순서로 실행합니다. Threads의 4편 연속글은 직전 게시 ID를 `reply_to_id`로 사용하고, 매 편의 성공 ID를 `publishedIds`에 확정 저장한 뒤 다음 편을 시작합니다. `publishedId`와 `permalink`는 첫 글을 가리킵니다. 선택적 링크 조회가 실패해도 확인된 성공을 실패로 되돌리지 않습니다.

외부 게시 요청이 타임아웃되거나 응답을 잃으면 실제 성공 여부가 불명확할 수 있습니다. `PUBLISH_UNKNOWN`과 `PUBLISH_PARTIAL`에서 새 컨테이너를 생성하거나 게시를 자동 재시도하지 않습니다. 먼저 공개된 글을 자동 취소하거나 남은 부분만 자동 재개하지 않으며, 호출자는 저장된 ID와 플랫폼을 직접 확인해야 합니다. 이 흐름은 외부 API와 DB 사이의 완전한 분산 트랜잭션을 보장하지 않습니다. MCP와 웹 프록시는 게시 응답을 최대 360초 기다립니다.

## 콘텐츠 스튜디오와 일괄 저장

`GET /content-studio/options`는 주제·표현 장치·말투를 반환하고, `POST /content-studio/generate`는 최대 12개의 4편 콘텐츠를 만듭니다. 외부 AI를 호출하지 않는 `TEMPLATE` 생성기이며 개인 운세 계산과 구분합니다. 미리 보기와 생성 시각만 반환하므로 자동 저장·게시 부작용이 없습니다.

Threads 초안은 `segments`에 4편을 저장하고 `text`는 1편과 같아야 합니다. Instagram에는 합친 캡션을 사용합니다. 단일 글의 `segments`는 빈 배열입니다. 수정 시 `segments` 생략은 나머지 편 유지, 빈 배열은 단일 글로 전환, 4편 배열은 전체 교체입니다.

`POST /posts/batch`는 1~12개 초안을 하나의 트랜잭션으로 저장하며, 하나라도 잘못되면 전체 취소합니다. `requestId`와 입력 지문을 저장하므로 동일한 키·입력은 같은 게시물 ID들을 반환하고 다른 입력은 충돌합니다. 응답 유실 후 저장을 확인할 때도 원래 키와 입력을 유지합니다. 이 저장 멱등성은 실제 게시 재시도를 허용하는 의미가 아닙니다.

## 개인 운세

`POST /fortunes/preview`는 출생 입력을 영구 저장하지 않는 계산 요청입니다. 양력·음력 및 윤달 입력을 백엔드에서 검증·변환하고, 선택한 역법 기준의 사주 기둥과 오늘의 문안을 반환합니다. 음력 날짜는 양력 `LocalDate`로 받을 수 없으므로 `birthDate`를 문자열로 전달합니다. 태어난 시각이 없으면 시주를 추정하지 않습니다.

응답에는 계산의 `basis`, 해석 한계를 설명하는 `notice`, 플랫폼별 문안이 포함됩니다. 운세 생성만으로 초안이 저장되거나 게시되지는 않습니다. 공개 문안에 원본 생년월일이나 태어난 시각을 추가하지 않습니다. 역법과 해석의 지원 범위는 반환되는 기준 설명을 따릅니다.

## AI 인터페이스

MCP의 15개 도구는 REST 요청을 전달하고 구조화된 오류 코드를 보존합니다. 운세·콘텐츠 미리 보기는 읽기·계산 도구, 일괄 저장은 멱등 쓰기 도구, 실제 게시는 외부 변경을 일으키는 비멱등 도구로 표시합니다. OAuth 코드는 브라우저에 묶어야 하므로 MCP로 노출하지 않습니다. [AI 연결 안내](ai-integration.md)

## 남은 운영 확장

사용자별 로그인·권한·계정 격리, 다중 계정, 토큰 자동 갱신, 일부 게시·결과 불확실 상태의 수동 복구 화면, 대량 목록의 페이지네이션·보관 정책은 별도 확장 작업입니다. 실제 예약 게시, 다른 사용자 댓글 관리·답글·인사이트, Reels·캐러셀 지원은 현재 모의 예약과 자신의 4편 답글 체인 흐름에서 확장해야 합니다.
